# NEA Script Runtime 0.1

The Demo runtime executes trusted local server scripts in a Node `vm` context without `process`, `require`, dynamic code generation, or WebAssembly. It is a compatibility prototype, not yet a hardened hostile-code sandbox.

The project format binds server and client entry modules to separate contracts, complete module lists, and separate capability lists. Server capabilities gate the Node VM globals below. The importer preserves all declared server CommonJS modules in the project package and publishes all declared client modules with `clientIndex.js` as the Player entry identity; client grants are never treated as server grants.

The server module loader supports the recovered CommonJS substrate: cached relative, package-root absolute, directory `index.js`, and bundled `node_modules` resolution, including circular partial exports and native module metadata. It does not execute ESM syntax. Capability generation therefore blocks server `import`/`export` syntax rather than claiming that dependency analysis alone makes it runnable.

Project assets are content-addressed and hashed during import, but packaging is separate from runtime consumption. The local server has no executable binding for the recovered `resources` global, and generic client `asset:` URL translation is not implemented. Capability generation therefore reports packaged images/audio as `partial`, missing assets as `blocked`, and mesh projection as `blocked` unless a capture-derived validated mesh binding is supplied by the runtime-package path.

Entity projection uses separate launch semantics. Static project entities are required world content, so an unvalidated mesh blocks startup. Script-created entities are allowed to remain local Runtime objects; an unknown mesh produces a `partial` projection record and does not fabricate a backend entity, mesh ID, bounds, collider, or physics body. A validated captured mesh binding is the only path that promotes the projection to `ready`.

Static client UI uses the recovered `gameUI.reset` state already accepted by the Player backend. When a source project supplies that state, the importer validates and republishes it and the launcher passes its manifest instead of enabling the minimal `gameUI` identity. Capability generation verifies literal global/default-screen `findChildByName` calls against the tree, blocks dynamic or missing lookups, and leaves uncertain receiver-subtree lookups `partial` rather than assuming a match.

Before either Runtime starts, the importer produces `capabilities/manifest.json`. The launcher rejects missing grants and declarations without executable bindings, warns for explicitly partial surfaces, and never widens capabilities to make a script start.

The Demo client requests `client.core`, `client.ui`, and `client.remote-channel`. Its `client.js` creates a historical Player `UiText` status panel and updates it from server events, making the independent SES client Runtime visible in-game rather than only through console logs.

## Globals

- `world`: tick, player lifecycle, voxel/general contact, trigger enter/leave, chat, entity creation, and tag queries.
- `voxels`: preserved BlockInfo-backed `id`, `getVoxelId`, `setVoxelId`, and `setVoxel` compatibility methods.
- `remoteChannel`: client-event subscription and authenticated outbound delivery to the matching MuDB Player session.
- `Vector3` and `Vec3.create`: minimal vector compatibility.
- `console`, `setTimeout`, `clearTimeout`, and `structuredClone`.

Every privileged API checks its declared capability at call time. `server.world.voxels` independently gates the `voxels` facade and the recovered `world.size` projection; possessing `server.world.entities` does not grant terrain reads or writes. Missing grants fail the script instead of silently widening access.

`server.gui` gates the documented `GameGUI` command/event/factory members. Projects may still attach their own state, constants, or helper functions to the shared `world` and `gui` globals. A surface established by a static assignment anywhere in the project module graph is reported as `script-owned`, not promoted into the DAO3 ABI and not rejected as an unknown Runtime member.

`server.storage` gates `storage.getDataStorage()` and `storage.getGroupStorage()` at both launch analysis and runtime access. Local single-map spaces preserve the recovered asynchronous key/value surface and durable project-local file storage. Group storage returns `undefined` unless the project package carries a launch-verified `storage.groupId`; enabled spaces include that id in their persistent namespace, preventing unrelated groups from sharing `group:*` keys. This remains a local provider rather than recovered DAO3 cloud storage.

`server.http` gates the recovered `GameHttpAPI.fetch` request surface. The local implementation performs host-side `http:`/`https:` requests only when its host explicitly supplies an exact `allowedOrigins` list; the default policy denies all network access. Redirects are rejected, logs contain only an origin rather than paths or query strings, timeouts are clamped to 60 seconds, and response bodies larger than the configured 4 MiB limit are rejected. The returned `GameHttpFetchResponse` exposes the recovered read-only `ok`, `status`, `statusText`, and `headers` fields plus `json()`, `text()`, `arrayBuffer()`, and `close()` methods. Non-2xx responses resolve with `ok === false`; scripts must treat this as an opt-in local transport, not proof of historical DAO3 network policy.

`server.world.config` gates the currently projected historical configuration properties `world.gravity`, `world.airFriction`, and `world.fogColor`, plus the read-only `world.projectName` identity. `world.projectName` is injected from the launch-verified `dao3.project.json.display.name`; Capability Manifest v14 binds the same normalized value before Runtime construction. Historical `world.url` and `world.serverId` are not synthesized because the local package and launcher do not provide authoritative DAO3 start values. Unknown project-owned `world.*` fields remain unaffected. Script writes to gravity or air friction now reconfigure runtime-owned Player bodies from the next tick using the recovered `airFriction ? velocityDamping` binding and exponential integration (`exp(-velocityDamping * deltaTicks)`). Existing project-package physics remains active until a script changes either property, so importing a package does not silently replace its configured local solver. The mutable physics and fog properties remain `partial`: the local `AuthoritativeGameRuntime` only arbitrates submitted transforms and the preserved Player game-net public schema explicitly marks world physics unused, so there is no recovered mutable browser-physics channel. Generic RuntimeEntity rigid bodies are also not integrated, while fog changes are not yet proven to propagate to every Player session.

## Voxel ABI

The server runtime loads the preserved BlockInfo asset referenced by the local Player world manifest and never synthesizes block names or IDs. The first conformance phase implements `voxels.id`, `voxels.getVoxelId`, `voxels.setVoxelId`, and `voxels.setVoxel` from `ScriptVoxelSync`, the dao3.fun GameVoxels documentation, ArenaPro declarations, captured editor declarations, and anonymous real-script call shapes. Full IDs retain the two rotation bits above the `0x3fff` base-type mask, successful writes immediately update both reads and collision candidates, and invalid names, IDs, or coordinates return `0` as in the historical source.

The recovered source contains mojibake in four Chinese rotation-alias cases. English aliases and numeric strings confirmed by the readable switch cases are implemented; the exact Chinese aliases remain an explicit compatibility gap until another local source recovers their original text.

The second conformance phase completes the basic read surface with `voxels.getVoxel`, `voxels.name`, and `voxels.getVoxelRotation` plus BlockInfo-backed `voxels.VoxelTypes` and the script-visible maximum `voxels.shape`. The anonymous corpus report separately marks direct script-defined assignments as `custom-extension`; undeclared names without assignment evidence remain `unclassified` instead of being promoted to either native ABI or work-specific behavior.
## Raycast ABI

`world.raycast(origin, direction, options?)` follows the recovered historical `ScriptWorldSync` flow rather than a work-specific adapter. The supported options are exactly the declared `maxDistance`, `ignoreFluid`, `ignoreVoxel`, `ignoreEntities`, and `ignoreSelector`. When `maxDistance` is omitted, the recovered default is `Infinity`; direction is normalized only when its magnitude exceeds the historical epsilon, so a zero vector is preserved instead of rejected. A no-hit result retains the requested distance and zero vectors for `hitPosition`, `normal`, and `voxelIndex`. Entity candidates are tested first, then the voxel ray is limited to the current nearest distance, matching the recovered dispatch order. The local finite voxel grid stops traversal at its world boundary so an infinite default cannot create an unbounded loop.

The return value is a `RuntimeRaycastResult` adapter with the nine directly recovered `GameRaycastResult` fields: `hit`, `hitEntity`, `hitVoxel`, `origin`, `direction`, `distance`, `hitPosition`, `normal`, and `voxelIndex`. `voxel` remains a local alias of `hitVoxel` and is not claimed as historical ABI. Capability analysis propagates variables assigned from `world.raycast(...)` as `GameRaycastResult`, and propagates a variable assigned from `.hitEntity` as `GameEntity`, so downstream member requirements are checked against the correct owners. The adapter remains partial: entity intersection uses local AABBs, entity values are the local RuntimeEntity/RuntimePlayer subset, and vector fields use the local `Vector3` compatibility type.

Entity ray intersections currently use authoritative player bounds or imported entity AABBs. The implementation of the historical engine `raycastBoxes` primitive and its body-orientation semantics is not present in the available source, so that portion remains explicitly partial. `GameWorld.useOBB` is documented and recovered as a separate world-physics property; it is not a `GameRaycastOptions` field and is not invented as one.

`world.addZone(config)`, `world.removeZone(zone)`, and the callable `world.zones()` surface follow the recovered `GameZone`, `ScriptZoneWrapper`, and `ScriptZoneSystem` lifecycle. Zone selectors are parsed, sorted, normalized, cached, and refreshed after script mutation; every Runtime tick excludes `collides=false` entities, polls the remaining queryable entities, expands the zone test by each entity's bounds, and emits `{ tick, entity }` through `onEnter`/`nextEnter` and `onLeave`/`nextLeave`. Removing a zone emits leave events for its active entities before destroying its listeners. Capability Manifest analysis propagates the returned `GameZone` owner instead of treating `area.onEnter()` and related calls as project-defined extensions.

Zone compatibility remains partial. Native physics-selector state, zone force/mass application, and fog/rain/snow/sky projection into the Player renderer are not implemented, and setting those recovered fields does not claim those effects occurred.

## Physics model

The complete collision-filter management surface is available: `world.addCollisionFilter(a, b)`, `removeCollisionFilter(a, b)`, `clearCollisionFilters()`, and `collisionFilters()`. The registry preserves ordered selector pairs, removes only exact ordered matches, deduplicates repeated additions, and returns fresh nested arrays. All four APIs remain partial because the local physics solver does not consume the registered selector pairs; registration is not presented as collision suppression.

Player positions represent the rigid-body center. Each server player receives an explicit initial collision profile containing origin status, size status, broadphase bounds and shape half extents; no solver default silently supplies a body size. The recovered upright Player default is `0.45 / 1.1 / 0.45`. Network PUBLIC bodies populate `rx/ry/rz` from `boundsHalfExtents` and `hsx/hsy/hsz` from `shapeHalfExtents`. A complete authoritative pair replaces the current collider, while an explicitly unknown posture shape (`null`) preserves it and a partial pair is rejected. This is a local compatibility policy, not a claim that crouch or flying historically used the standing size. Candidate lookup uses bounds while actual contacts and triggers use shape. Player snapshots expose both sets, `collision.shapeSource`, `collision.aabb`, and `collision.shapeAabb`. Mutations such as `player.applyImpulse()` and `player.damage()` require `server.player.write`.

`runtime.snapshot().physics` exposes sweep, chunk-query, candidate, trigger-query, chunk, collider, and trigger counts for diagnostics. The model runs at the project tick rate (20 Hz in the Demo). It remains a server Script Runtime model and does not overwrite the historical Player motor every frame.

## Contact force ABI

Recovered solver evidence defines each contact force as the normal and friction impulses accumulated during a fixed step, multiplied by `INV_DT`. The local sweep solver therefore records its actual collision and ground-friction velocity deltas and projects `force = mass * deltaVelocity / deltaTime` into `GameVoxelContactEvent.force`. Simultaneous contacts divide the impulse evenly, matching the recovered voxel-contact compaction rule that copies the group-average force to each retained contact. DAO3 documentation supplies the native default mass of `1`; no aggregate `GameEntity.contactForce` value is synthesized because the historical `ContactBinding` aggregation implementation remains unavailable.

Voxel contact and separation callbacks receive a `RuntimeVoxelContactEvent` carrying the eight directly declared fields `tick`, `entity`, `x`, `y`, `z`, `voxel`, `axis`, and `force`. The historical ScriptShell proves construction from physics contact packets and world-before-entity dispatch; the local producer preserves that order. `player`, `collider`, `normal`, and `compatibility` remain local diagnostics and are not claimed as historical event fields. Capability analysis propagates inline and named callback parameters for `onVoxelContact`, `nextVoxelContact`, `onVoxelSeparate`, and `nextVoxelSeparate` as `GameVoxelContactEvent`. Compatibility remains partial because entities and vectors are local subsets and the collision solver is not the recovered native rigid-body engine.

Fluid contact production uses preserved BlockInfo fluid ids and the authoritative Player body's current AABB. Each tick computes active fluid voxel overlaps, emits a typed `RuntimeFluidContactEvent` with the recovered `tick`, `entity`, and `voxel` fields to the world listener before the entity listener, and exposes active `{ voxel, volume }` records through `fluidContacts`. Capability analysis propagates inline and named parameters for `onFluidEnter`, `nextFluidEnter`, `onFluidLeave`, and `nextFluidLeave` as `GameFluidContactEvent`. The local `volume` value is explicitly the body-AABB overlap fraction. Historical producer timing, its exact volume-fraction formula, buoyancy, and drag are not recovered, so all fluid surfaces remain partial.

`GameTickEvent.elapsedTimeMS` follows the recovered `Date.now() - previousDispatchMS` formula rather than the configured interval constant, and `skip` follows `tick - prevTick > 1`. The local scheduler currently advances exactly one tick per callback, so ordinary local events report `skip: false`; no authoritative multi-tick frame ingress or native catch-up scheduler is invented.

## Authoritative Player state

Players created from real MuDB sessions use `authority: "backend"`. Their position, velocity, `bodyHalfExtents`, and `bodyShapeHalfExtents` are polled from the compatibility backend's existing `AuthoritativeGameRuntime`; local physics observes contacts and triggers without applying a second gravity/movement simulation. Script writes to `player.position`, `player.velocity`, or `player.applyImpulse()` are optimistically reflected, protected by a short write barrier, and queued back through the backend's existing transform command path. Runtime-only test players continue to use the local fixed-step physics owner.

## Entity lifecycle ABI

`GameEntity.addTag(tag)`, `removeTag(tag)`, and `hasTag(tag)` now have direct canonical adapters on both `RuntimeEntity` and `RuntimePlayer`. They preserve the documented `void`, `void`, and `boolean` results while using the recovered string-keyed tag set. `GameEntity.tags()` remains partial because the local compatibility object exposes a mutable `Set<string>` property instead of the documented array-returning method; native tag replication is also not claimed.

The readonly `GameEntity.isPlayer` discriminator is also canonical on both local object types: `RuntimeEntity` returns `false` and `RuntimePlayer` returns `true`. This does not imply that the adjacent writable `GameEntity.player` declaration is complete.

Player join/leave and entity create/destroy callbacks now receive a typed `RuntimeEntityEvent` with the recovered `tick` and `entity` fields. The local `player` property remains an alias of `entity` for compatibility with existing project scripts and is not claimed as historical `GameEntityEvent` ABI. Capability analysis propagates inline and named callback parameters for `onPlayerJoin`, `nextPlayerJoin`, `onPlayerLeave`, `nextPlayerLeave`, `onEntityCreate`, `nextEntityCreate`, `onEntityDestroy`, `nextEntityDestroy`, and entity `onDestroy` / `nextDestroy`; variables assigned from `event.entity` continue as `GameEntity`. For player join/leave, the subscription is project-ready because both historical and local producers dispatch the exact `GameEntityEvent { tick, entity }` payload and every accessed `GamePlayerEntity` member is gated separately. The repository-wide `GamePlayerEntity` ABI and independent native engine lifecycle ingress remain partial.

`GameEntity.destroy()` now follows the recovered server lifecycle instead of hiding or disabling an entity locally. A non-player entity is removed from Script Runtime selectors immediately, resolves `onDestroy` and `nextDestroy` once, and requests authoritative backend despawn when it has a recovered projection binding. Player destruction remains a no-op, matching the historical `ScriptEntitySync.destroyEntity` non-player guard. Runtime-created entities remain local until the separately evidenced entity-creation projection path is implemented.

This bridge is required for collision correctness as well as script compatibility: removing only the script wrapper would leave the projected rigid body in the authoritative runtime and produce an invisible collider. The implementation therefore uses the backend's existing despawn path rather than introducing a work-specific collision exception.

## Runtime-created entity projection

`world.createEntity()` still returns its `GameEntity` synchronously and emits the recovered entity-create event immediately. Its documented physics and render configuration (`position`, `velocity`, `bounds`, `collides`, `fixed`, `gravity`, `mass`, `friction`, `restitution`, `mesh`, `meshScale`, and `meshOrientation`) is then sent through a loopback-only bridge to the existing authoritative entity registry. `bounds` follows the recovered body-center half-extents convention, is validated as a positive finite vector during creation, and is exposed through a detached readonly copy. The same initial value is stored in authoritative `replica.body.bounds`. Subsequent whole-value `position`, `velocity`, `collides`, `fixed`, `gravity`, `mass`, `friction`, and `restitution` assignments use the authenticated entity-state path and update authoritative `replica.body` state after backend type/range validation. Whole-property updates to `meshInvisible`, `meshScale`, `meshOrientation`, `meshOffset`, `meshColor`, `meshMetalness`, `meshEmissive`, and `meshShininess` now use the same path and update the protocol-backed authoritative model/body fields. Dynamic `mesh` replacement remains forbidden because scripts cannot change the validated bootstrap `meshId`; `anchorOffset`, nested vector/quaternion/color mutation, and RuntimePlayer model bindings remain unimplemented, so the model APIs stay `partial`. The recovered `showEntityName`, `customName`, `nameRadius`, and `nameColor` defaults are also implemented for validated captured-mesh RuntimeEntity instances. Enabling the name creates an authoritative `nameplate { text, radius, color }` component, later whole-property writes update it, and disabling the name removes it from the replica. RuntimePlayer nameplate behavior and nested `nameColor.r/g/b` mutation are not bridged, so these canonical fields remain `partial`. RuntimePlayer exposes a copy of its current authoritative `boundsHalfExtents`. `GameEntity.bounds` is executable but remains `partial` because complete native oriented-body and posture-producer coverage is unavailable. This is state replication only: the local authoritative runtime still does not integrate generic RuntimeEntity rigid bodies, so collision response, fixed-body enforcement, gravity motion, mass response, friction, and restitution remain partial rather than claimed native behavior.

The editor-package builder adds only captured model metadata/data to the Player bootstrap table and writes a validated mesh-name-to-bootstrap mapping. The backend refuses to project a mesh absent from that mapping; it does not substitute a model, derive bounds from a name, or turn an unknown mesh into a work-specific placeholder. Unmapped entities remain visible to server scripts but are explicitly not claimed to be browser/physics replicas.

## Damage ABI

Writes to `showHealthBar`, `hp`, and `maxHp`, together with `GameEntity.hurt()` and `GamePlayer.forceRespawn()`, now use the recovered `replica.damage` state and `game-net` `scriptEvents.damage` transport. Hurt amounts for the same entity and server tick are aggregated before emission, matching the historical ScriptShell behavior. Death and respawn are emitted as the recovered entity-ID lists, while health-bar state remains in the public replica snapshot.

Each script-produced hurt emits a typed `RuntimeDamageEvent` with the recovered `tick`, `entity`, `damage`, `attacker`, and `damageType` fields to the damaged entity before the world listener, matching the historical ScriptShell order. Capability analysis propagates `onTakeDamage` / `nextTakeDamage` callback parameters as `GameDamageEvent`, and variables assigned from `event.entity` or `event.attacker` as `GameEntity`. This remains partial because authoritative native DamageBinding ingress outside script-produced damage has not been recovered.

When that script-produced hurt crosses hp from positive to zero, the runtime emits a typed `RuntimeDieEvent` with the recovered `tick`, `entity`, `attacker`, and `damageType` fields to the dying entity before the world listener. Capability analysis propagates `onDie` / `nextDie` callback parameters as `GameDieEvent` and nested entity owners. This remains partial because independent native death-state production has not been recovered.

Local `forceRespawn()` emits a typed `RuntimeRespawnEvent` containing only the recovered `tick` and `entity` fields, to the respawned player before the world listener. Capability analysis propagates `onRespawn` / `nextRespawn` callback parameters as `GameRespawnEvent` and `event.entity` as `GamePlayerEntity`. Automatic native respawn production remains unverified, so the family stays partial.

Recovered `player.entity-interact` ingress emits a typed `RuntimeInteractEvent` with `tick`, the initiating `GamePlayerEntity`, and the mapped target `GameEntity`. The target listener runs before the world listener, matching the historical shell. Capability analysis propagates both nested owners. The event remains partial because the local backend does not project the native interactive component, prompts, radius selection, or sounds, and unmapped targets cannot receive browser-originated interactions.

Tick callbacks receive a typed `RuntimeTickEvent`. `tick`, `prevTick`, `skip`, and `elapsedTimeMS` are the canonical recovered fields; `deltaTime` is retained only as a documented local seconds-based extension. The historical wall-clock elapsed formula and skip predicate are implemented, but the local scheduler has no authoritative multi-tick frame input, so native delayed-frame catch-up remains partial.

Chat signal payloads use a typed `RuntimeChatEvent` containing only `tick`, `entity`, and `message`; the previous local `player` alias is not part of the recovered ABI. Capability analysis propagates the event and nested entity owner, but `world.onChat` and `world.nextChat` remain startup blockers because no Player/browser-to-server chat ingress has been recovered. The typed object does not create or imply that transport path.

Purchase-success signal analysis uses a typed `RuntimePurchaseSuccessEvent` with `tick`, `userId`, `productId`, and `orderId`. The recovered `market-script` family proves marketplace-open and acknowledgement messages but no event producer into the Server Script Runtime. Therefore `world.onPlayerPurchaseSuccess` and `world.nextPlayerPurchaseSuccess` remain startup blockers; the object factory exists only for ABI/conformance and is not an ingress substitute.

Keyboard callback payloads are represented by `RuntimeKeyBoardEvent` with the recovered `tick` and `keyCode` fields. Historical ScriptShell consumes `keyDownState` and `prevKeyDownState`, but the recovered local Player input packet only contains button bitmasks. `RuntimePlayer.onKeyDown` and `onKeyUp` therefore have no producer and are blocked at project startup rather than being conflated with action-button press/release ingress.

Canonical entity-to-entity contact subscriptions are startup-blocked. Historical `bodyContact` / `bodySeparate` events require two mapped entities plus axis and force, while the local solver currently produces voxel and generic collider contacts and sets canonical `other` evidence unresolved. Local `world.onContact` / `onContactSeparate` remain explicit extensions and are not mapped to `GameWorld.onEntityContact` / `onEntitySeparate`.

Generated Runtime ABI signatures use the corresponding typed event names wherever a typed payload implementation exists. Anonymous structural signatures remain only for local generic collider, trigger, and RemoteChannel payloads that do not have an evidence-backed canonical event object.

`enableDamage` remains a Script Runtime gate because it does not appear in the recovered client `DamageSchema`. Damage generated by the native engine outside server scripts is still a separate unresolved ingress path; the bridge does not invent combat rules, weapon semantics, or work-specific health behavior.

## Input and click ABI

The backend forwards recovered `game-net.input.events` packets only when the explicit Script Runtime bridge is enabled. The server Runtime applies the exact captured input bit assignments for ACTION0, ACTION1, JUMP, WALK, CROUCH, RUN, DOUBLE_JUMP, and FLY. Before reconstructing events it applies the historical ScriptShell permission mask from `GamePlayer.enableAction0`, `enableAction1`, `enableJump`, `enableDoubleJump`, and `enableCrouch`, and updates the declared `action0Button`, `action1Button`, `jumpButton`, `walkButton`, and `crouchButton` state. It reconstructs each press/release as a typed `RuntimeInputEvent` with `tick`, `entity`, `position`, `button`, `pressed`, and `raycast`, then dispatches the same object first to `world` and then to the player. ACTION0/ACTION1 presses that hit an authoritatively bound entity additionally create a typed `RuntimeClickEvent` with the declared `GameClickEvent` fields (`tick`, `entity`, `clicker`, `button`, `distance`, `clickerPosition`, and `raycast`) and dispatch the same event object first to `world.onClick`, then to the clicked entity's `onClick`, matching the recovered ScriptShell order. Both event types nest `RuntimeRaycastResult`. Capability analysis propagates input/click callback parameters and variables assigned from their entity, clicker, or raycast members to the corresponding owners. Public Player flags are not yet written back to the browser client, so disabling an input is currently authoritative at server event dispatch rather than at client control generation.

Static hit resolution is intentionally not guessed from project IDs. The backend emits its actual legacy/projection `entityId` bindings, and the Script Runtime binds those to imported source IDs or entity indexes. Editor runtime packages may append mesh bootstrap entries only when the capture contains the project node, mesh asset hash, model metadata, secondary model body, and matching bounds. Entities missing any part of that evidence remain explicitly unmapped. Project-package-safe carrier tags are kept separate from captured source tags so server scripts retain the original DAO3 tag values without weakening package validation.

## Event Future ABI

DAO3 event channels and futures are intentionally distinct. Recovered `GameEventChannel<EventType>` accepts only `onX(handler)`; it does not have a listener filter argument. Recovered `GameEventFuture<EventType>` exposes `nextX(filter?)`. The local EventSignal now mirrors historical `ScriptDispatcher`: regular handlers run first, a future whose filter returns false remains pending, a filter exception is reported through the event error path but the current event still resolves that future, and clearing the dispatcher rejects pending futures. World, entity, player, and RemoteChannel `nextX` methods all forward the optional filter without adding work-specific predicates.

## GUI ABI

The server `GameGUI` surface now uses the recovered Player `gui` MuDB protocol end to end. `init`, `show`, `remove`, `getAttribute`, and `setAttribute` allocate a monotonic native handle, serialize the exact recovered fields, wait for the Player's `return` or `throw` response, and reject pending calls when the GUI socket is replaced or disconnected. The browser remains responsible for selector matching and attribute mutation, so the local runtime does not invent DOM-like behavior.

Client `sendMessage` packets are emitted by the backend as a structured loopback event, mapped back to the authoritative RuntimePlayer, and dispatched through `GameGUI.onMessage` with the recovered `{ entity, name, payload }` shape. The `gui.ui` proxy follows the historical `GameGUI.js` factory exactly: it returns `{ name, attributes, children }` without adding local validation or work-specific element names.

## Current bridge boundary

The runtime observes real Player joins and receives opted-in client events through a structured backend log bridge. Outbound events use a random-token, loopback-only HTTP control bridge and are injected into the matching remote-channel MuDB session. The Demo also reconstructs the historical `gameUI` identity required before Player client modules can start.

## Chat output ABI

`world.say(message)` and `GamePlayer.directMessage(message)` now cross the Server Script Runtime boundary into the preserved Player's recovered `game-chat.log` MuDB protocol. World messages are delivered to every connected game-chat session; direct messages are sent only to the target player's bound session with the recovered private flag. The packet uses the directly recovered text-message defaults (`id=0`, `msgType=0`, `duration=0`, empty i18n fields, `valid=true`).

Capability Manifest analysis records this outbound dependency as `transport:chat-delivery` for `world.say`, mapped entity `say`, and player-targeted messaging. The dependency requires the `chat-delivery` runtime flow and `player.game-chat` protocol family. `world.onChat` and `world.nextChat` are inbound surfaces with a different transport direction: the historical event shape is recovered, but no Player/browser chat ingress reaches the local Server Script Runtime, so projects depending on those world events are blocked with `chat-ingress-unavailable`.

`GameEntity.say(message, options?)` uses the same native packet with the entity's authoritative backend id, recovered `duration` conversion (`Infinity` becomes `-1`), and `hideFloat`. This projection is intentionally available only for entities that already have an authoritative binding. A script-local entity with an unknown or unprojected mesh keeps its local call record but does not receive a fabricated Player id or floating bubble.

Outbound entity/player chat now also follows the recovered lifecycle gate. A destroyed entity sender or removed player receiver is silently ignored before logging or transport. Player removal marks the Runtime player destroyed and dispatches the recovered `world.onPlayerLeave` ? player `onDestroy` ? `world.onEntityDestroy` order. The recovered FIFO structure sends a configured prefix immediately, buffers overflow in order, drains it before the next tick, and resets the counter. Overflow crosses the Server Runtime-to-backend control boundary as one ordered deliveries array before the backend projects each item to the recovered Player `game-chat.log` message. The limit defaults to `null`, meaning unthrottled delivery, because local evidence does not contain the numeric `MAX_CHATS_PER_TICK` value. Player display acknowledgement and browser-to-server chat ingress remain unrecovered, so chat compatibility stays partial.

Click, press, and release subscriptions add a separate `transport:input-event-ingress` dependency. This flow begins in the Player browser client's recovered `player.game-net.input` packet, passes through the backend input handler and launcher event parser, and ends at `ScriptRuntime.dispatchInputEvents()`. The Runtime applies the recovered PlayerFlags mask and reconstructs `GameClickEvent`/`GameInputEvent` payloads using the historical `ScriptShell` algorithm. This is not a Client Script Runtime flow, and it does not prove keyboard-event, chat, or arbitrary browser input ingress.

`world.onInteract` / `nextInteract` and entity-local interaction subscriptions add `transport:entity-interact-ingress`. The archived Player selects synchronized interactive targets, sends the recovered `{ id, tick }` message over `player.entity-interact`, and waits for `acknowledgeInteract`; the launcher maps that authoritative entity id back to a local RuntimeEntity and dispatches one `{ tick, entity, targetEntity }` object to the target before the world listener. This remains `partial`: the local backend still marks `replica.interactive` unused, so setting `enableInteract` does not synthesize browser prompts, interaction radius selection, sounds, or a physics target. Unmapped and script-local entities cannot receive browser-originated interaction.

Input delivery does not make every click target complete. Player clicks and backend-bound entities can be projected; a non-player script entity without a validated authoritative backend binding remains unable to receive a fabricated hit id. `onClick` therefore remains partial where that limitation applies.

`world.searchBox(bounds)` returns Runtime entities and players whose axis-aligned body bounds overlap the supplied `GameBounds3`. It uses the same recovered body-center half-extents convention as `GameEntity.bounds`, zones, and raycasts. The adapter remains partial because native oriented-body search and `world.useOBB` are unavailable.

`world.entityQuota()` returns `entityLimit - nonPlayerEntityCount`, matching the recovered `ScriptEntitySync` formula. Static non-player entities and successful script-created entities consume quota; players do not. The package value is launch-bound by Capability Manifest v14 and defaults to the recovered protocol identity `3400`. At zero quota, `world.createEntity()` logs the recovered limit error, returns `null`, and does not emit an entity-create event or create an authoritative replica.

`world.sound(...)`, mapped `GameEntity.sound(...)`, and authoritative Player `sound(...)` use the recovered `player.sound` MuDB protocol. The returned `Sound` object emits the recovered resume, seek, pause, and stop messages. Capability Manifest v14 extracts literal string samples and literal `sample` fields from statically resolved server sound calls, requires a packaged `player-block-audio` dictionary binding for each, and adds `transport:sound-playback`. Dynamic sample expressions remain ABI-visible but do not prove resource availability. Browser decode/playback completion and `ClientAudio.mediaError` are not acknowledged to the Server Runtime, so these APIs remain `partial`.

`GameEntity.lookAt(targetPosition, meshFacing = "Z", up = new GameVector3(0, 1, 0))` reproduces the recovered `ScriptEntityWrapper` algorithm, including target/up coercion, invalid-facing warning and Z fallback, zero-direction +Z fallback, parallel-up perturbation, the distinct X/Y/Z matrix layouts, and the historical gl-matrix component order written into `GameQuaternion.set`. RuntimeEntity calls assign `meshOrientation` as a whole and therefore use the existing authoritative body-orientation bridge. RuntimePlayer model orientation and nested quaternion mutation remain unavailable, so the canonical method is `partial`.

`GameEntity.rotateLocal(localPosition, axis, rad)` reproduces the recovered pivot rotation algorithm in radians. It transforms the local pivot with `meshScale` and the historical nonstandard `meshOrientation` component interpretation, applies and normalizes the selected X/Y/Z quaternion rotation, then compensates `position` by the difference between the old and new transformed pivot. RuntimeEntity whole-property orientation and position updates use their existing authoritative bridges. Invalid axes are rejected because the recovered source has no fallback. RuntimePlayer model orientation and nested quaternion/position mutation remain unavailable, so the method is `partial`.

`GameEntity.scaleLocal(localPosition, scale)` replaces `meshScale` and preserves the selected local pivot's world position by applying the recovered transform before and after the scale change. RuntimeEntity whole-property scale and position assignments reuse their existing authoritative bridges. RuntimePlayer model scale and nested scale/position mutation remain unavailable, so the method is `partial`.

`GameEntity.anchorOffset` remains startup-blocked. Local evidence proves the declaration and separately recovers per-mesh render-box and rigid-body offsets, but no source proves which offset populates `anchorOffset`, its sign, scale/orientation treatment, mesh-change refresh lifecycle, or write synchronization. RuntimeEntity therefore does not expose a fabricated zero vector; projects reading this field receive a precise Capability Manifest evidence blocker.

Damage mutations use a distinct `transport:damage-state-projection` dependency. Calls to `hurt()` and `forceRespawn()`, plus writes to `hp`, `maxHp`, or `showHealthBar`, first update Script Runtime state and synchronously emit the local recovered lifecycle event where applicable. The authenticated local control bridge then projects the resulting damage state to the authoritative runtime, which publishes recovered `PUBLIC.damage` state and aggregates `hurt`, `die`, and `respawn` script events for Player sessions.

Reading damage properties or subscribing to `onTakeDamage`, `onDie`, or `onRespawn` does not by itself require this outbound projection. Those operations consume Script Runtime state/events; they do not mutate authoritative state. Unmapped script-local entities keep their local damage lifecycle without receiving a fabricated backend entity id or Player health projection.

Dynamic entity projection uses a runtime whitelist derived from the already-approved Capability Manifest. A `world.createEntity()` call with a literal mesh marked `validated-mesh` adds the `authoritative:runtime-entity-projection` dependency and may use the authenticated create/state/destroy control bridge. The backend independently resolves the same name through the captured projection descriptor before it creates a replica. This double check prevents a script from turning an arbitrary string into geometry, bounds, collision, or an authoritative body.

Unknown, dynamic, or unvalidated mesh names remain ordinary Script Runtime entities. They still participate in selectors and local lifecycle events, but transform writes and destruction never call the backend projection callbacks because no authoritative id is assigned.

Entity selectors follow the recovered `ParsedSelector` implementation rather than CSS syntax. Commas form an OR union; `*` and `entity` match every non-destroyed entity, `player` matches players, `#value` matches `GameEntity.id`, and `.value` matches a tag. `world.testSelector` uses the documented `(selector, entity)` order. Whitespace does not create an intersection selector, and display `name` is not substituted for `id`. `world.querySelectorAll()` returns a fresh mutable array in recovered entity order; mutating it does not mutate the Runtime's authoritative entity collection. Selector compatibility remains partial because the historical `testComponent` implementation for component names other than `player` / `entity` is absent from the recovered source.

`storage.getDataStorage()` returns a local `RuntimeDataStorage` with the documented key, CRUD, update, increment, list, remove, and destroy shape. Results preserve `{ key, value, version, createTime, updateTime }`, and `RuntimeQueryList` uses cursor as a page index. `set` and `update` recursively enforce the recovered `JSONValue` union: strings, finite numbers, booleans, dense arrays, and plain string-keyed objects are accepted; null, undefined, non-finite numbers, functions, symbols, BigInt, sparse arrays, cycles, and class instances are rejected instead of being silently rewritten by JSON serialization. All local mutations share one process-local queue: asynchronous `update` handlers and concurrent `increment` calls complete without same-process lost updates. Local list queries cap `pageSize` at 100, traverse at most five `constraintTarget` levels, warn and fall back to the stored value for invalid or missing paths, apply numeric `min`/`max`, and order same-type scalar targets. This is a project-local JSON implementation, not recovered DAO3 cloud storage: byte quotas, distributed ticket atomicity, backend error codes, cross-process consistency, exact natural order, and mixed-type ordering remain partial. `storage.getGroupStorage()` is blocked by the default Capability Manifest because no authoritative group identity/provider exists; it is available only when an embedding explicitly proves and enables that scope.

Player dialogs use `transport:dialog-rpc` over the recovered `player.dialog` protocol. `GamePlayer.dialog(config)` opens a native Player dialog and resolves its promise from the matching close RPC result (`close`, `text`, `input`, or `select`). `GamePlayer.cancelDialogs()` crosses the authenticated local control bridge and cancels every pending dialog for that Player session using the recovered `cancelDialogs` packet.

`world.onPlayerPurchaseSuccess` is declared with the recovered `GamePurchaseSuccessEvent` fields `{ tick, userId, productId, orderId }`, but it is not launchable locally. The saved market protocols prove marketplace-open and acknowledgement messages only; no Player/browser or backend path produces a purchase-success event for the Server Script Runtime. Capability Manifest therefore emits the blocking `purchase-success-ingress-unavailable` diagnostic instead of treating the generic event-dispatch shell as a commerce implementation.

Dialog support remains partial. The directly recovered common fields and dialog type union are normalized, but completeness of every historical `GameDialogCall` option and all exception/timing behavior is not yet proven. The backend cancellation count is internal; the script-facing `cancelDialogs()` keeps the documented `void` result.

Player join and leave handlers add `transport:player-session-lifecycle`. The Player backend derives an irreversible `session-sha256-?` bridge label from the MuDB session id, emits that stable label for game-net join and disconnect events, and uses the same matcher for subsequent input, GUI, RemoteChannel, dialog, state, and damage control operations. The launcher rejects legacy truncated labels before creating or removing a `RuntimePlayer` wrapper. Disconnect removal preserves the recovered order `world.onPlayerLeave` ? `player.onDestroy` ? `world.onEntityDestroy` and passes the same `GameEntityEvent { tick, entity }` object to all three dispatchers.

This identity is intentionally local and anonymous. It prevents prefix/suffix collisions without exposing the original session id, but it does not recover a DAO3 user id, profile, account name, or complete `GamePlayerEntity` surface. The repository-wide player ABI therefore remains partial. A concrete project's join/leave subscription can still be ready because its event payload is exact and every player member used by that project is gated independently.
