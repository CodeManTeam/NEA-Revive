# AI 协作开发流程

> 适用于 NEA-Revive 的 AI 辅助开发、审查和调试。目标是让复杂工作保持在正确方向上，
> 同时避免为了流程而增加过多工具和文档负担。

## 一、先锁定边界

每项工作开始前，先写清楚五件事：

1. **目标**：这次要让什么行为变得可用或可验证？
2. **范围**：只允许修改哪些模块或文件？
3. **非目标**：明确这次不做什么，避免顺手扩张。
4. **依据**：使用哪些 API 文档、原始脚本、历史 bundle、协议帧或截图？
5. **验收**：什么现象、测试或构建结果代表完成？

关键方向不清楚时，先和用户确认；不要用实现细节替用户做产品决定。

## 二、项目硬约束

- 原始地图脚本不修改。
- 不为单张地图制作 adapter。
- 不在通用引擎中加入地图名称分支。
- 历史 API 要在通用运行时中原生支持。
- 新增能力必须同时参考：DAO3 API 文档、原始脚本调用、历史证据。
- 地图 UI 与引擎系统 UI 分层，不能互相清除或污染。

## 三、标准工作循环

```text
确认目标
  -> 读取任务文档和相关代码
  -> 检查 git 状态、HEAD 和工作区差异
  -> 用 rg 找到真实调用点和当前实现
  -> 建立最小假设
  -> 用最低成本的 probe 验证
  -> 做最小修改
  -> 先跑针对性测试，再跑完整验收
  -> 检查 dist/运行环境
  -> 独立复查并更新文档
```

### 1. 先做状态快照

```powershell
git status --short
git diff --stat
rg -n "目标符号|事件名|协议名" .
```

同时确认当前工作目录。仓库根目录和 `backend/box-go` 的命令不能混用相对路径。

### 2. 先验证，再修改

按成本从低到高：

```text
语法检查
  -> 单元/协议测试
  -> 最小 Playwright probe
  -> 后端集成测试
  -> 浏览器 smoke
  -> trunk build
  -> 完整运行栈
```

浏览器问题优先检查真实状态，而不是猜测：

```js
document.querySelector(selector)
document.activeElement
getComputedStyle(element)
element.getBoundingClientRect()
```

### 3. 每次只验证一个主要假设

用下面的格式记录推理：

```text
现象：按 T 后输入法出现，但输入框不可见。
假设：输入框已创建并获得焦点，但坐标在视口外。
验证：检查 activeElement 和 getBoundingClientRect()。
结论：确认/排除假设。
修改：只修复定位公式。
```

不要同时修改 UI、协议、Rust 状态机和构建配置来“试试看”。

## 四、证据优先级

实现历史兼容能力时，按以下顺序交叉核对：

1. DAO3 API 文档：公开契约、类型、参数和生命周期。
2. 原始地图脚本：项目真正调用的能力和流程。
3. 历史 bundle、dump、WebSocket 帧、UI 树和截图：真实实现细节。
4. 当前测试和运行结果：本地实现是否达到目标。

如果来源冲突，不要静默选择。记录文档定义、脚本依赖、历史行为、当前选择和未解决差异。

## 五、修改和验收规则

### 修改前

- 先说明准备改哪些文件。
- 先确认没有覆盖用户已有改动。
- 任务范围不明确时先问，不以猜测扩大范围。

### 修改后

- `node --check` 检查 JavaScript 语法。
- 后端按需运行 `npx tsx --test src/*.test.ts`。
- 前端运行对应 `cargo test`。
- 前端源码变化后运行 `trunk build --release`。
- 用 probe 或浏览器 smoke 验证用户实际看到的状态。
- 不以“代码看起来正确”代替运行结果。

### 审查时

- 不直接相信执行者的回填。
- 独立重跑关键命令。
- 检查源文件、`dist` 和浏览器实际加载内容是否一致。
- 明确区分 `已证明`、`推断`、`未验证` 和 `已知差异`。

## 六、和用户的交互方式

- 用短问题确认高影响方向：定位、范围、脚本是否可改、验收标准。
- 用户回答后，先复述成明确决策，再继续下一步。
- 方向一旦确定，停止重复询问，进入执行。
- 把长期有效的决策写入总计划或 `AGENTS.md`，避免下次重新讨论。
- 汇报时只说四件事：完成了什么、验证了什么、还缺什么、需要用户决定什么。

## 七、避免过度工程化

- 优先使用现有命令、测试和文档，不为一次性问题新建框架。
- 临时 probe 用完即删；只有重复使用时才沉淀为测试或工具。
- 一个任务只解决一个主要问题，不顺手重构相邻模块。
- 先达到可验证的最小闭环，再扩大范围。
- 流程的目的，是减少返工和方向错误，不是增加审批步骤。

## 八、快速检查表

```text
[ ] 目标和非目标已确认
[ ] 修改范围已确认
[ ] API/脚本/历史证据已找到
[ ] git 状态和工作目录已确认
[ ] 已建立一个可验证假设
[ ] 已做最小修改
[ ] 针对性测试通过
[ ] 构建产物已更新
[ ] 浏览器实际状态已验证
[ ] 结果和剩余差异已记录
```
